# P1 Sell: mini-spec

Baseline: Master Specification v1.0, Sections 7-11 and 13. Status: draft, 2026-10-06.

## Goal

A store can sell on the Pi hub: products with packs and singles, BC tax, the till from open to close, cash and standalone-card payments, receipts, returns and exchanges, stock by phone, labels and a product import. Tills keep selling when the hub is unreachable.

**Done when** (Section 13 phase gate): all Must requirements below pass their tests; offline selling works; permissions are enforced on the hub; every write is in the event log; lists export to CSV/Excel; tested on the Pi with 3 devices and a power pull mid-sale; backup and restore verified; piloted for a week (with P0, DL-63). **The P1 release is blocked until the accountant confirms the tax rules (open question Q1).**

## Design decisions (step 1)

| ID | Decision |
| --- | --- |
| DL-64 | Stock and cost are kept in the product's **base unit** (`each`, `kg` or `lb`). Each selling unit has a `base_qty` the hub computes from its nesting (a case of 4 packs of 6 = 24). Product `cost_cents` is per base unit; a unit's cost is cost × base_qty, so margin is shown per unit |
| DL-65 | Barcodes stay a list on each selling unit (Section 10). One barcode belongs to one product; units of the same product may share it, which triggers "packs or singles?" (FR-6.03, Q7). PLUs are unique among products. The hub checks both on every save |
| DL-66 | A product saved as Active that fails BR-07 is refused with a list of what is missing; the import and the phone form save it as a Draft with those reasons instead (FR-11.05). `draft_reasons` is computed by the hub. One open task lists the Drafts (BR-08) |
| DL-67 | Price history is written by the hub in the same transaction as the price or cost change (alongside the event log). Making a product Active, or changing a price on an Active product, needs `prices.edit` (manager, owner); staff with `catalogue.edit` create products as Drafts and may update costs. The first price of a new unit is recorded too (0 → price) |
| DL-68 | Tax rates are rows with effective dates: GST 5% (federal) and BC PST 7% are seeded; other provinces and HST arrive as tax-table updates (FR-12.03). Tax classes: Standard (GST+PST), GST only, Zero-rated, Exempt; owners can add custom classes. **All tax data stays marked "pending accountant review" until Q1 is answered** |
| DL-69 | Weighed products need the Weighed Goods module; age limits and deposits/fees need Regulated Items. A product using a switched-off module stays a Draft |
| DL-70 | Table rules run **inside the change's transaction**: `lib/event_log.js` calls a table's `beforeWrite()` (checks) and `afterWrite()` (dependent writes) around each save, so checks cannot race and dependent writes roll back with the change. The "before" state comes from the database, not `record.original()`, which is stale when one record object is saved twice |
| DL-72 | **Cashiers do not see costs or margins** (Sreya, 2026-10-06). Permission `costs.view` (owner, manager, accountant, staff, who enter costs when receiving). Without it the hub hides `cost_cents` and the amounts of cost-history rows in every API answer, including realtime |
| DL-73 | Stock = loose base units + sealed packs per selling unit; on hand = loose + sealed × base quantity. Opening a case gives its inner packs; opening a pack of singles gives loose units. Lots carry expiry and cost per base unit; a lot's cost may have decimals of a cent (a case of 24 at $20.00 = 83.33 ¢ each), product costs stay whole cents (BR-01) |
| DL-74 | Stock changes only through `/api/chedam/stock/...`, one transaction per request; a whole receiving grid commits or nothing does. Each request carries an `op_id` made on the device; a repeat returns the first result (BR-10) |
| DL-75 | Lowering stock always needs a reason from `stock.reasons` (BR-05). A staff write-off worth more than `stock.approval_value_cents` (default $25, at cost) waits for a manager (`stock.approve`) and raises the "stock:approvals" task; managers' own write-offs post at once (BR-18, FR-6.06) |
| DL-76 | Receiving a perishable without an expiry uses today + shelf life; products marked "expiry entered at receiving" must have one. Write-offs and counts take expired lots first; sales (step 3) skip expired lots unless a manager overrides (BR-14). A count records "expected" when each line is counted, so sales during the count are not variance |
| DL-77 | A 12-digit UPC-A code and the same code with a leading 0 (EAN-13) are one barcode: lookup finds either form and uniqueness checks both. Found while testing the camera reader, which (like USB scanners and Android's reader) may report a 0-led EAN-13 as UPC-A |
| DL-78 | Camera scanning: the browser's BarcodeDetector where it reads EAN-13 (Chrome on Android), else ZXing (`@zxing/library` 0.23.0, Apache-2.0) loaded only when needed and cached for offline. Retail 1D formats only (EAN-13/8, UPC-A/E, Code 128/39, ITF); the middle band of the picture is read about 8 times a second. Typing and USB scanners always work as well. When the camera is refused, the app says why (untrusted certificate, permission, no camera) |
| DL-79 | **The hub prices every sale again.** The till sends the cart (product, unit, quantity, discount, override, payments); the hub recomputes prices, discounts, tax and totals, checks stock and approvals, and completes the sale in one transaction. The sale id is made on the till, so a repeat returns the first result (BR-10); if the till's total differs from the hub's, the sale is refused with the hub's prices. The arithmetic is a pure module (`lib/pricing_core.js`) the offline till can share in step 4 |
| DL-80 | Tax: cart discounts are spread over lines by amount (largest remainder) before tax (BR-21); tax is summed per tax type and rate for the receipt and rounded once, half up (BR-22); each line keeps its share (FR-4.06). Tax-included stores have the tax taken out of the prices. Deposits and eco fees are never discounted; their own tax class applies (pending Q1) |
| DL-81 | Manager approval on the till = the manager's PIN, which gives a one-time approval valid 5 minutes covering that sale's exceptions (discount above `sales.discount_limit_pct`, price lowered beyond `sales.override_limit_pct`, selling expired stock) or a void. Wrong PINs count toward the manager's lockout. People holding `sales.approve` need no approval for their own sales. Who approved is stored on the sale |
| DL-82 | Payments: cash is rounded to 5 ¢ only when cash finishes the sale (BR-16); cards are exact and cannot exceed what is due; declined card attempts are kept; US cash at `sales.usd_rate` with change in Canadian dollars; store credit and platform payments arrive with their modules |
| DL-83 | Packs at the till (FR-3.05): if a line needs more loose items or packs than are sealed, the till asks "open a pack?"; on yes the hub opens the smallest pack that serves it (case → packs → loose) and records each pack break. Expired lots are sold only with approval and only when fresh lots are not enough (BR-14) |
| DL-84 | Tills: one open till per device, opened with a counted float. Expected cash = float + cash taken − change given for US cash − drops − pay-outs + float added; US cash is counted on its own. Pay-outs need `till.manage`; no-sale needs a reason. Closing writes the Z report; over or short by more than `till.variance_task_cents` ($5) raises a task. A sale can be voided (manager) only while its till is open; afterwards it is a return (step 6). Training sales get T- numbers, never touch stock or money, and are counted on the Z report |
| DL-85 | Soft holds (BR-13): when a cart holds an item with `sales.soft_hold.units` (3) or fewer on hand, it is held for that cart for 5 minutes; other tills see only what is left. Released on sale, removal or expiry |
| DL-86 | **The till prices offline with the hub's own code.** `hub/pb_hooks/lib/pricing_core.js` is served to the app at build time as `virtual:pricing-core` (no copy); the till's cart rules (`client/src/lib/offline_price.js`) mirror the hub's and a test checks both give the same totals, taxes and line shares to the cent. The till keeps an offline pack (products, sellable units, prices, tax tables, deposits, settings, receipt header; no costs) in IndexedDB (Dexie 4.4.6), refreshed whenever the hub answers |
| DL-87 | **Offline sale:** when the hub does not answer, the till completes the sale itself with an offline receipt number `OFF-<device>-<n>`, prints the receipt from its own figures and queues the sale on the device; if storage fails it says so and the sale is not finished. A sale whose hub request timed out is finished offline with the same sale id, so if the hub had it after all the upload returns the first result (BR-10) |
| DL-88 | **Upload:** queued sales upload in order every 10 s while the hub answers (`POST /api/chedam/sales/offline`). The hub records what was charged: it checks the arithmetic (same module) and that payments cover the total, but does not re-price; it gives an S- number and keeps the offline number. Stock may go negative (BR-12): an urgent "oversold while offline" task per product, closed by itself when stock is back at zero or more. A sale arriving after its till closed is kept, noted and raises a task; a refused sale stays on the till marked for a manager. The till cannot close while sales wait. Payment methods switched off since are still accepted |
| DL-89 | **Offline limits:** anything needing a manager's PIN is refused offline (only the hub checks PINs); signing in needs the hub, but the person already signed in keeps selling, also after the till reloads (their details are kept on the device and used only with their own unexpired token). No stock check offline. Holds, recall and voids need the hub |
| DL-90 | **Opening the till offline** (Sreya's test 2026-10-07: with the hub off before opening, nothing could be sold): the till counts the float on the device and opens; the opening waits in the upload queue ahead of that till's sales, keeps its device-made id (a repeat is answered with the first result) and the device's opening time if plausible (last 24 h); the hub numbers it on arrival. If another till was still open on that device it is recorded anyway, with a note and a task. Cash drops, pay-outs, no-sale and closing still need the hub, so the Z report has every sale |
| DL-91 | **Printing through the hub:** the hub lays out receipts and till reports (`lib/receipt_layout.js`, plain ASCII for code page 437) and sends ESC/POS bytes to the network printer on raw TCP (port 9100) with `pb_hooks/bin/printer.sh`. Printing runs after the sale is saved and never undoes it; a printer that does not answer gives a message and the till's browser print is the fallback (also for sales made offline). Printers are the setting `printing.printers`; a device uses its `assigned_printer`, or the store's only printer, or none ("none"). Network scan: the hub's /24, port 9100, 32 hosts at a time |
| DL-92 | **Cash drawer only for a recorded event:** it opens with the receipt of a cash (or US cash) sale taken on that device in the last 10 minutes, once; or for a no-sale recorded on that device in the last 2 minutes, once (FR-3.11). Reprints never open it. A manager's test print can open it from the Receipt printer screen |
| DL-93 | **Receipt content (FR-3.13, NFR-14):** GST/HST and PST registration numbers and tax by type on every receipt (covers the CRA $30 tier); from `printing.receipt.full_receipt_cents` ($150) the cashier can add the buyer's name and "Terms: paid in full" (full GST/HST receipt). Total, then cash rounding, then "Total in cash" (BR-16). Savings, return barcode (CODE128 of the sale number, not on training receipts), training and void banners, reprints marked "COPY (reprint n)" and counted on the sale. Loyalty summary waits for the loyalty module; customer display (FR-1.11) is not in this step |
| DL-94 | **Refund amount (BR-23):** each returned line gives back its share of what was paid: net after the line discount and its cart-discount share, its tax per type and rate as stored on the sale line, and its deposit, in proportion to the quantity (half up); the return that brings a line to its sold quantity takes exactly what is left, so several partial returns never refund a cent more or less than was paid. Tax-included sales refund the price paid (the tax is inside it). Weighed items return by weight (3 decimals). A sale with returns, or an exchange sale, cannot be voided: it is returned instead |
| DL-95 | **Return policy (FR-4.07, BR-17, Q2 defaults):** settings `returns.window_days` 30 (a category's `return_window_days` wins), `returns.cashier_limit_cents` $50, `returns.lowest_price_days` 30, `returns.restocking_fee_pct` 0. A manager's PIN (one-time approval, as for sales) is needed for: a refund over the limit, a sale past the window, an item or category marked non-returnable, and any return without a receipt. People with sales.approve approve their own. New permission `sales.return` (cashier, manager) |
| DL-96 | **No receipt (FR-4.10):** store credit only, at the lowest price of that selling unit in the last 30 days (current price and price history; the $0 "old price" recorded when a product is created is ignored) with today's tax and deposits. **Store credit (FR-3.08):** a code SC-XXXX-XXXX printed with its barcode on the return slip; spent at the till by scanning or typing it (hub checks the balance; partial use keeps the rest; a voided sale gives it back). Offline tills cannot take store credit. Codes are listed only for sales.view / till.manage |
| DL-98 | **Label batch (FR-5.13, BR-25):** one pending line per product and selling unit; a new price on a unit of a product on sale, or a product going on sale (all its till units), adds it by itself when the Labels module is on; adding by scan, category or search merges into the same line (reasons kept: new price, new product, added). Promotion, promotion-end and markdown labels come with promotions (P2). Permission `labels.manage` (manager, staff) |
| DL-99 | **Printing labels (FR-5.15, 5.16):** the app draws an exact-size PDF in the browser (jsPDF 4.2.1, loaded only on the Labels screen; vector barcodes: EAN-13/UPC-A/EAN-8 when the check digit is right, else CODE128; checked by decoding with ZXing, also from a 300 dpi render). "Make the PDF" saves a batch: a snapshot of each label's content, the layout and the template. "Printed fine" takes its lines off the batch, except a line that changed after the batch was made (a new price): it stays to print again. The last 10 printed batches can be printed again (with the prices printed then). Presets: Letter 3×10, Letter 2×5, A4 3×8, plain Letter/A4 3×8 with cut lines, 2×1 in roll; custom layouts (rows × columns × sizes × margins × gaps), checked to fit the page; printer offset; start position on a partly used sheet; alignment test page with a 50 mm ruler |
| DL-100 | **Label content (FR-5.14):** name (2 lines), French name, size, origin ("Product of X / Produit du Canada" or "Origine : X"), price with /kg or the pack name, unit price, barcode or PLU (produce), store logo; a smaller price rather than a barcode too narrow to scan. Products get a size (size_qty, size_unit g/kg/mL/L/items) for the unit price: per 100 g / 100 mL by default, or per kg / L; weighed goods per 100 g (kg) or per kg (lb); multi-item packs per item. Struck regular price and promotion text wait for promotions (P2) |
| DL-101 | **Import reading without DuckDB (changes DL-03 for imports):** DuckDB-WASM is about 35 MB per browser bundle, which the Pi Zero would serve and every deploy would copy. Product files are at most a few thousand rows, so the back-office reads them with small libraries, loaded only on the Import screen: Papa Parse 5.7.0 (CSV/TSV/text, delimiter), SheetJS 0.20.3 from the vendor's own channel (Excel; the npm copy is an old version with known vulnerabilities), hyparquet 1.31.2 (Parquet), fflate 0.8.3 (zip); encoding by BOM, then strict UTF-8, else Windows-1252. DuckDB can still come for analytics (P2 insights), loaded from the internet on a back-office computer |
| DL-102 | **Product import (FR-11.02-11.07):** at most 2000 rows a job. Header row found among the first 10 rows. Columns mapped by synonyms (English, French, Square/Shopify/Lightspeed/Clover/Loyverse/QuickBooks names), letter-pair similarity and the values (barcodes, PLUs, money), with high/medium/low confidence; values outrank a weak name guess. Transforms: money ("$1,234.50", "3,99 $"), barcodes Excel shortened (lost leading 0 put back only when the check digit proves it), sizes and "6x355ml" packs in names, "English / Français" names, country names to codes, sold by kg/lb; tax-included prices converted on the hub at the class's rates. The hub checks each row (create / update / skip by barcode, PLU or name; errors stop the row; Draft reasons; warnings) and imports in ONE transaction: all or nothing, with a job record also when it fails. Complete rows become Active, others Drafts with reasons (DL-66); without prices.edit (staff) all new rows are Drafts and existing prices are left alone. Missing categories created on request. New products go to the label batch unless switched off. Opening stock is not imported (receive it) |
| DL-103 | **Exports (FR-11.09, NFR-22):** Products, Stock and Sales lists export what is shown to CSV (UTF-8 with BOM, RFC 4180), Excel or PDF. The full business export (permission `data.export`, owner only) makes one zip in the owner's browser: every store table as CSV and JSON, a data dictionary (tables, fields, types, links, "money in cents") and a README. Hidden fields (password and PIN hashes, device keys, tokens) and PocketBase's own tables are never sent |
| DL-104 | **Till reconciliation (FR-10.01):** per till: cash expected vs counted (its Z report), card total vs the card terminal's settlement for that till (entered by a manager with the batch number), sales that reached the till after it was closed (offline uploads, recomputed now vs the Z report), returns. Flags: cash over/short beyond `till.variance_task_cents` ($5), settlement not entered, terminal above/below the till, sales after closing, still open. Reconciling (till.manage) needs a note when cash, card or late sales do not balance; who and when are recorded. Readable with sales.view (accountant) |
| DL-105 | **Loss prevention (FR-10.11):** per cashier for a period: sales, voided sales (with who approved), removed lines, discounts, price overrides (amount lowered), no-sales, refunds (no receipt; on sales they rang up themselves; cash), tills closed short. Rates per 100 sales or % of sales; flagged when a rate is `reports.flags.multiple` (2×) the store's with at least `min_count` (3) events, plus 2+ no-receipt refunds, 2+ refunds on own sales, 2+ tills short. Each cashier's events listed with time, receipt, amount and reason. A flag is a reason to look, not proof (said on screen) |
| DL-106 | **Audit log viewer and retention (FR-10.13, 10.09, BR-34):** the event log (same transaction as each change) filtered by dates, person, device, table, action and record id or text; 50 a page; what changed shown before → after (create/delete: the values), people shown by name; cost fields removed without costs.view; secrets were never logged. The app already only marks records deleted; hub code that deletes on purpose (soft holds, sample data, migrations) does not go through the API |
| DL-107 | **NFR-05 on the Pi Zero (P1 gate):** a sale takes the hub a median 0.45 s, but the 95th percentile is 1.1-1.7 s when several tills pay at once or a burst of offline uploads arrives (the time is in the writes: every record of a sale and its audit entry in one transaction, synchronous=FULL). Measured, not hidden: docs/gate/P1-gate.md |
| DL-108 | **Lists of tables with costs, at most 200 a page (P1 gate):** the cost-hiding hook runs once per record; it is now a small module (lib/costs_hook.js) with "may see costs" cached 10 s per person in the hub's store, and app users get at most 200 rows a page of products, price history, stock lots and movements, sales, sale lines, returns and return lines (400 above; the admin account and hub code are not limited). | DL-97 | **Refunds and exchange (FR-4.13, 4.14):** refund in cash (rounded to 5 cents when cash finishes it, BR-16; leaves the drawer and the Z report's expected cash), to the card on the standalone terminal (up to what the card paid on that sale, less card refunds already given; the cashier confirms it went through), or store credit.
