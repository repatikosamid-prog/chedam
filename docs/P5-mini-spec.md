# P5 Connect and enrich: mini-spec

Baseline: Master Specification v1.0 (Sections 7, 8, 12, 13; FR-3.21, 3.22, 4.14, 11.01, 11.08, 11.10, 11.11, 12.05, 12.06, 12.08, 12.10; R1; D1, D2). Status: **started 2026-10-11** (Sreya: "continue to P5, deploy to the Pi"). Sprint 5. Built the same way as P2-P4: each step gets its own hub test suite, a client build, a deploy and a commit; the full test runs wait for the next test week.

## Goal

Chedam talks to the services a store already uses, and knows more about its products: the card terminal wakes up when the cashier presses **Card** (the store's own processor, Square first), card refunds go back through it, the processor's real fees fill in by themselves; the owner's Google Drive or OneDrive gets the encrypted off-site backup and a summary the owner can read away from the store; imports take every kind of record with ready mappings for the systems stores move from; reference data suggests product details without ever overwriting them; support can be let in for a while when the owner asks.

**Done when** (Section 13 phase gate): every Must below passes its tests; linked payments fall back to standalone mode when the internet or the processor is down (a card payment is never blocked); permissions on the hub; every write in the event log; no secret (processor token, cloud token, keys) in the event log, an export or the API; tested on the Pi with 3 devices and a power pull mid-sale; backup and restore verified.

## Build order

| Step | Delivers | Requirements |
| --- | --- | --- |
| 1. Payment processors and Square connect | The common payment interface (one adapter per processor) and the Square adapter; the owner connects the store's Square account and location; terminals paired to tills with a code; a fake Square for tests | FR-3.21, 3.22 (DL-114) |
| 2. Linked card payments at the till | **Card** sends the amount to the till's terminal; the till waits for approved / declined / cancelled; the hub records card brand, last 4 and the processor's payment id itself; cancel from the till; standalone fallback | FR-3.21 |
| 3. Linked refunds, fees and payouts | Card refunds on returns and voids back to the same card through the processor (Interac on the terminal); the real fee per payment and the processor's payouts fetched, so card fees and bank matching fill in | FR-4.14, 10.05 |
| 4. Cloud drive connection and off-site backup | The owner connects Google Drive or OneDrive (device code sign-in, app's own folder only); the nightly encrypted backup is also copied there, the newest kept | FR-12.08, D2 |
| 5. Owner remote view | Every 15 minutes (setting) the hub uploads an encrypted summary (sales today, tills, alerts, stock warnings, tasks); the owner's phone reads it away from the store, read-only, with "last updated" | FR-12.05 |
| 6. Import everything, mapping templates | Imports for customers, vendors, stock counts, sales history, bills, employees; saved mappings (Square, Shopify, Lightspeed, Clover, Loyverse, QuickBooks, Xero, Wave, Zoho, generic) chosen by themselves from the file's columns | FR-11.01, 11.08 |
| 7. Reference data | Datasets installed as signed packages (units, tax presets, shelf life, HS / Canada tariff, Open Food Facts subset, nutrients, currency history); they **suggest** in product, vendor and receiving screens and never overwrite; licences in Settings → About | FR-11.10, 11.11 |
| 8. Remote support session | The owner switches on a support session for a few hours (outbound tunnel, no port forwarding), sees who connected, switches it off; it ends by itself | FR-12.10 |
| 9. Gate | 3 devices, power pull mid linked payment, backup + restore, Pi load, the test sheet | Section 13 |

FR-12.06 (manager remote access, Could) moves to the web store sprint: it needs the store's own public address and tunnel, which that sprint sets up (DL-214).

## First design choices

| ID | Decision |
| --- | --- |
| P5-a | **One payment interface, one adapter per processor** (`lib/payproc.js` + `lib/payproc_square.js`): connect, locations, pair a terminal, checkout, status, cancel, refund, payment details, fees and payouts. Clover, Helcim, Stripe Terminal and Moneris are later adapters behind the same calls (DL-114) |
| P5-b | **The hub calls the processor, never the till** (outbound HTTPS only; no port forwarding). The till asks the hub, and the hub records what the processor says: a linked card payment can't be typed in or made up on a device |
| P5-c | **Secrets live encrypted on the hub** (the processor's access token, cloud refresh tokens) with the hub's own key, like SIN (P4-b): never in the API, the event log, exports or the data export; the owner sees only "connected as …" and can disconnect |
| P5-d | **Card payments are never blocked:** with no internet, no terminal or a processor error the till offers today's standalone dialog (key the amount in, record the result) |
| P5-e | **Sign-in to Google and Microsoft by device code** (the owner types a short code on google.com/device or microsoft.com/devicelogin): no web address on the hub has to be reachable from outside. The app's own folder only (Drive `drive.file`, OneDrive `Files.ReadWrite.AppFolder`). Needs the Google and Microsoft app registrations (D2); until then the screens show "waiting for the app registration" and the tests use fakes |
| P5-f | **Reference data suggests, never overwrites** (FR-11.11): a suggestion is shown beside the field with its source and is used only when someone taps it |

## Decisions (2026-10-11)

| ID | Decision |
| --- | --- |
| DL-214 | **The web store runs on the store's own Pi** (Sreya, 2026-10-11; replaces option A of DL-114, a static host). The plan for that sprint: the shop is a **separate process under its own user** with a read-only copy of the catalogue (photos, prices, "in stock / few left / sold out") that the hub refreshes, so the shop never touches the hub's database; it is reached through an **outbound tunnel** on the owner's domain (Cloudflare Tunnel: no port forwarding, the TELUS modem has none); online checkout on the processor's hosted page (Square, the same account as the terminal, P5 step 1), paid orders come back to the hub as pick-up orders with stock reserved; rate limits, and the shop stops itself before it can slow the tills. Production hardware is the Pi 4 (the Pi Zero 2 W is for development). The trade-offs written in the proposal (the shop is down when the store's power or internet is) are accepted. Manager remote access (FR-12.06) uses the same tunnel and is built there |

## Design decisions (step 1)

| ID | Decision |
| --- | --- |
| DL-215 | **Connecting the processor (FR-3.21, 3.22)**, Home → Card processor (`payments.connect`: owner only, sensitive): the owner pastes the account's **access token** from the processor's developer dashboard (Square: Sandbox to try, Production for real) and chooses the store's location (the main one is picked by itself). The hub checks the token with the processor (merchant, locations; the account must work in CAD) before saving. One processor at a time: connecting again replaces the old one. Square's sign-in page (OAuth) is not used because it needs an address on the internet to come back to; a token per store is Square's way for a business's own application |
| DL-216 | **Secrets (P5-c):** the token is sealed with the hub's own key (`pb_data/chedam-secrets.key`, made on first use) in a hidden field; it is never in an answer, the event log, exports or the data export, and is wiped on disconnect. **Found and fixed:** the backups saved the database and the HTTPS certificate authority but not the hub's key files, so after a restore on a new card the SIN and bank details (P4) could not be read. `chedam-backup` now saves `pb_data/chedam-*.key` beside each backup (`.keys`, encrypted with the backup key) and the restore puts them back (the current ones kept aside) |
| DL-217 | **Terminals:** "Pair a terminal" asks the processor for a **device code**, shown on the screen until the terminal signs in with it (checked every few seconds; Square codes expire after 5 minutes). Each terminal is linked to at most one till and each till to at most one terminal (linking takes it from the other). The till only learns whether Card is linked there and the terminal's name (`GET /api/chedam/payproc/till`). Setting `payments.linked` (on, how often the till asks, how long a checkout may wait) switches linked payments off for every till. Tests and the dev hub use a fake Square (`tools/devhub/fake-square.mjs`, `CHEDAM_SQUARE_BASE`) |

## Design decisions (step 2)

| ID | Decision |
| --- | --- |
| DL-218 | **Card on a linked till (FR-3.21):** when the till has a paired terminal, the hub is reachable, the sale is not a training sale and linked payments are on, **Card** shows the amount (changeable for a split) and **Send to the terminal**. The hub creates the processor's checkout for that terminal with the sale's id as its reference; the till asks the hub every 2 seconds (setting) and the hub asks the processor. Approved: the card payment is added with the card type and last 4 from the processor. Cancelled on the terminal, a declined card that the customer gives up on, or nothing after 5 minutes (setting; cancelled on the terminal): the till says why and offers Try again or **Key it in instead** (the standalone dialog). The cashier can cancel from the till; a payment that was approved a moment before the cancel is kept. One checkout at a time per terminal; asking again for the same sale and amount gets the same checkout |
| DL-219 | **The hub fills linked payments (P5-b):** a card payment that names a checkout must be an approved checkout of that sale for exactly that amount, not used by another sale; the hub writes the card type, last 4, the processor and its payment id (anything the till sent for those is ignored). Training sales can't take a linked payment. Standalone card payments still work on a linked till |
| DL-220 | **A card paid but no sale saved:** the till keeps the sale's id with the cart while a terminal payment exists, so a reload or a refused sale (e.g. the total changed) brings the paid card back into the payments when Pay is pressed again; Hold is refused and Clear asks first. Paid checkouts that no sale took after 15 minutes are listed for managers (`GET /api/chedam/terminal/checkouts`) to refund in step 3 |

## Design decisions (step 3)

| ID | Decision |
| --- | --- |
| DL-221 | **Card refunds through the processor (FR-4.14 stage 2):** a return of a sale paid on the linked terminal offers **Back to the card** (up to what those payments have left). The hub sends the refund to the processor first: Visa, Mastercard, Amex and others go back without the card; **Interac needs the card**, so it is sent to this till's terminal (else the one it was paid on) and the customer taps it. The return then names the refund and the hub checks it went through, for that sale, that return and that amount, and was not used before; the refund line gets the last 4 and the processor's reference. Asking again for the same return gives the same refund back (nothing is refunded twice); a refund whose return was refused is picked up again when the return is tried again |
| DL-222 | **Voids of a linked sale:** the card payments on the terminal go back to the card first (Void asks, then the refund as above, for the whole linked amount); the void names those refunds and is refused without them. Paid checkouts that no sale took (DL-220) are listed on Sales for managers (`sales.void`) with **Refund to the card** |
| DL-223 | **Fees and payouts (FR-10.05):** every hour (when connected and online) the hub asks the processor for the fee of each linked payment of the last 7 days that it did not know yet, and the payouts of the last 45 days. Card fees: a day the bank has not shown yet uses the processor's own fee for payments on the terminal and the estimate for the rest; the P&L estimate follows. Fees and statements lists the processor's payouts (and "Get fees and payouts now") to use when matching card deposits by hand in Bank; matching payouts automatically is left for later |

## Design decisions (step 4)

| ID | Decision |
| --- | --- |
| DL-224 | **Cloud drive (FR-12.08, P5-e)**, Home → Cloud drive (`cloud.connect`: owner only, sensitive): Google Drive (scope `drive.file`: only files Chedam made, in a "Chedam" folder) or OneDrive (`Files.ReadWrite.AppFolder`: the app folder), one at a time. Sign-in by **device code** (the screen shows a code to type on google.com/device or microsoft.com/devicelogin and notices by itself when it is done). Needs the store's **app registration** (D2): a client ID (Google: a "TVs and limited input devices" OAuth client and its secret; Microsoft: an Entra app with public client flows on), entered on the screen until Chedam ships its own. The secret, the refresh and access tokens are sealed (DL-216) and never shown; disconnect wipes them; an expired or removed sign-in is said on the screen ("connect the cloud drive again") |
| DL-225 | **The off-site backup copy:** when a cloud drive is connected, the backup helper also leaves the verified encrypted files of each backup (`.db.gz.age`, `.keys`, `.ca`, `.sha256`) in `pb_data/backup/outbox` (only the newest set). Every 5 minutes the hub uploads them (binary, through `curl` with the token in a 0600 header file, never on the command line; the backup file last, so a set in the cloud is complete once it is there), removes them from the outbox and keeps the newest `cloud.backup_keep` (14) sets in the cloud. A failed upload stays in the outbox and is tried again. The backup is the same file as on the USB drive: without the printed backup key it can't be opened. Limits: OneDrive's simple upload takes files up to 250 MB; a backup that size would need chunked upload (later). A backup without a USB drive (cloud only) is not offered yet |

## Design decisions (step 5)

| ID | Decision |
| --- | --- |
| DL-226 | **The summary (FR-12.05):** what the owner's dashboard shows, with costs: today against the same day last week, the month against the same days of last month (sales, transactions, margin), the P&L month to date, what needs attention (open tasks, approvals, unreconciled tills, stock warnings), open tills (number, who, since), who is clocked in, stock counts (out, low, expired, expiring), the last good backup and the hub's health problems. Built every `remote.view` minutes (15; on/off) and put on the connected cloud drive as `chedam-summary.enc` (replacing the last one), outbound only. Owner only (`cloud.connect`): Home → Cloud drive shows when it last went and "Send the summary now" |
| DL-227 | **Encrypted for the owner's devices:** the summary is encrypted on the hub with the **remote view key** (`pb_data/chedam-remote.key`, AES-256-GCM, in the backups with the other keys). **Enrol this device** (owner, at the store) gives that device the key and a read-only way to the file: the cloud drive's client ID (and Google's secret) and the refresh token, kept in the device's storage. Enrol only the owner's own devices; the sign-in can only see Chedam's own files (DL-224). **Forget enrolled devices** makes a new key: devices enrolled before can't read the next summaries (and the cloud sign-in can be removed in the Google or Microsoft account) |
| DL-228 | **Away from the store** (`#away`, no hub, no sign-in): the app opens from its cache, signs in to the cloud drive with the refresh token (Microsoft's new refresh tokens are kept), downloads the summary and decrypts it with WebCrypto; it shows "last updated" and how long ago, and the last summary it read when the cloud can't be reached. When the hub can't be reached, every screen of an enrolled device offers "Away from the store? See the latest summary". The reader (`client/src/lib/remote_read.js`) is the code the hub tests run. **To check with the real registrations (D2):** the browser calls to Google's and Microsoft's sign-in (cross-origin); Microsoft may need the app registered as a single-page app as well |

## Design decisions (step 6)

| ID | Decision |
| --- | --- |
| DL-229 | **Every kind of record (FR-11.01):** Import and export → **Import other records**: customers (loyalty members; the store must confirm they agreed to a loyalty program in the old system; first names only; points carried over as an adjustment), vendors and clients (with one contact; existing ones skipped or updated), opening stock (quantities on hand and cost for products with no stock yet, as a receiving "Opening stock"; products with stock are skipped: use a count), open bills and invoices (what is still owed on the day Chedam starts, one "Opening balance" line, no tax; a bill already recorded is skipped) and staff (owner only: a person with no PIN or device yet, and the employee record; SIN checked and encrypted, never in the job record). Same steps as products: file → columns → check on the hub (errors, warnings, exclude) → one transaction, all or nothing, in the import log. Each import needs its screen's permission; the Import screen opens for anyone with one of them. Sales history is not imported (later) |
| DL-230 | **Mapping templates (FR-11.08):** built-in column layouts of exports from Square, Shopify, Lightspeed, Clover, Loyverse, QuickBooks, Xero, Wave and Zoho per kind of import (`client/src/lib/import/targets.js`); the file's column names pick the best fitting one (prefixes such as Loyverse's "Price [store]") and the mapping is filled in, to be checked. The store saves its own mappings by name (`import_templates`); its own come first. Without a template, suggestions from the column names and values as before. Dates (ISO, month or day first, Excel numbers), money, terms ("Net 30"), countries and full names are converted in the browser |
| DL-231 | **Found and fixed:** the full data export's table groups did not have the P5 tables (the P1 suite caught it); they are in "Card processor and cloud drive" and "Store settings". Hidden fields (tokens, secrets) stay out of every export |

## Design decisions (step 7)

| ID | Decision |
| --- | --- |
| DL-232 | **Reference datasets (FR-11.10)** ship with the hub's code as read-only SQLite files with a manifest (source, licence, version, rows) in `pb_hooks/reference/`, built by `tools/datasets/build.mjs`; they come with app updates and stay **out of the store's database** (backups and the cloud copy stay small). The hub reads them with the `sqlite3` command (on the PC: `tools/devhub/sqlite3-node.mjs`, Node's own SQLite). Shipped now, written for Chedam: **units** and conversions, **Canadian sales tax rates by province** (as of 2026-10-01; NS HST 14%), a **shelf-life starter guide** (general food-safety guidance, about 80 items; the package date comes first) and the **97 HS chapters** |
| DL-233 | **Asked online, one item at a time** (outbound, no keys, a 6-second limit, remembered for the day, setting `reference.online`): **Open Food Facts** for a barcode (name with brand, French name, size, their category; ODbL, credited) and the **Bank of Canada** for an exchange rate on a day (the last business day on or before it). Offline: "not available", nothing else changes |
| DL-234 | **Suggest, never overwrite (FR-11.11):** Product: "Suggest from the barcode" (name, French name, size: each with Use), shelf life "Suggest" (Use 7 / 30 / 180 days), HS "Find" (Use the chapter). Exchange rates: "Suggest the Bank of Canada rate" (Use, with the source filled in). Tax: the rates of every province, for reference only. Help → **About Chedam** lists every dataset and online source with its licence. Waiting for Sreya's OK to download (large, from their publishers): the Open Food Facts Canada subset for offline lookups, the CBSA Customs Tariff (10-digit codes), the Canadian Nutrient File, USDA FoodData Central, FoodKeeper, India ITC-HS and Bank of Canada history; each gets its own builder then |

## Design decisions (step 8)

| ID | Decision |
| --- | --- |
| DL-235 | **Remote support session (FR-12.10)**, Home → Remote support (`support.manage`: owner only, sensitive): the owner keeps the public SSH keys of the people who may help (setting `support.keys`; add, remove) and, when help is needed, presses **Let support in** for 1, 2, 4 or 8 hours. The root helper `/opt/chedam/bin/chedam-support` (request/result files and a path unit, like the backup helper) then: makes the user `chedam-support` (no password), writes the keys with OpenSSH `expiry-time` (they stop working at the end time by themselves), gives sudo for the session only, and starts an **outbound** Cloudflare quick tunnel to the hub's SSH (a `trycloudflare.com` address: no account, nothing opened on the store's router). A systemd timer ends it at the end time even if the hub is not running; **End now** ends it at once (keys and sudo removed, sessions closed). The screen shows the address and the command to give support, and the support sign-ins seen; every session is recorded (who switched it on and off, when) |
| DL-236 | **The tunnel program `cloudflared` is not installed on the Pi yet**: the screen says so when support is switched on. It is also what the web store will use (DL-214), so it is installed once, with Sreya's OK, from Cloudflare's own package repository; `deploy.sh` reports whether it is there |
