## Why SSH keys instead of a password

With a key pair, the private key never leaves the PC and the Pi holds only the public key. No secret crosses the network, keys cannot be guessed, and scripts can log in, so password login is switched off.

| File | Where | Rule |
| --- | --- | --- |
| `id_ed25519` | PC `C:\Users\Venkata\.ssh\` | Private. Never share, paste or commit; back it up privately |
| `id_ed25519.pub` | PC, same folder | Public, one line ending `chedam-dev`. Safe to copy |
| `authorized_keys` | Pi `/home/chedam/.ssh/` | Allowed public keys; folder 700, file 600 |
| `known_hosts` | PC `.ssh\` | Remembered Pi identities; `ssh-keygen -R <ip>` after a re-flash |
| `config` | PC `.ssh\` | Alias `ssh chedam` |

Key procedures recorded:

- create the key pair
- put the public key on the Pi with Imager (REMOVE old keys, then BROWSE to the `.pub` file)
- add or replace keys with `type new.pub | ssh chedam "cat >> ~/.ssh/authorized_keys"`
- what to do when locked out (monitor + keyboard, or re-flash)

## Steps

1. Backed up `.ssh` with `Copy-Item $env:USERPROFILE\.ssh $env:USERPROFILE\.ssh_backup -Recurse`.
2. Cleared old host fingerprints by deleting `known_hosts` and `known_hosts.old`. There was a backup.
3. Router: changed the admin password, set the LAN to `192.168.50.1/24` (different from TELUS `192.168.1.x`), kept it in router mode, and turned on 2.4 GHz.
4. Re-flashed the card. Imager: Pi Zero 2 W, Lite 64-bit, `chedam`/`chedam`, new Wi-Fi, CA, SSH public-key only.
5. Found the Pi in the router's DHCP client list and created the reservation.
6. Updated the SSH config to `HostName 192.168.50.101` and removed `HostKeyAlias`.
7. Ran `sudo apt update && sudo apt full-upgrade -y` and checked that `sshd -T` shows `passwordauthentication no`.
8. Readiness check: model, OS, IP, active Wi-Fi, `multi-user.target`; reboot test passed.
9. Forced HDMI output (see below).

## Failed cases and fixes

| Attempt / symptom | Cause | Fix |
| --- | --- | --- |
| `ssh-keygen -R <old-ip>` errored | PowerShell treats `<` as an operator | Use real addresses; deleting `known_hosts` avoided needing the old IP |
| Key pair deleted during "start fresh" | Not needed: a key is not tied to a network | Restored from `.ssh_backup` |
| `ssh 192.168.50.101` denied as `venkata` | No user given, so the Windows name was used | `ssh chedam@192.168.50.101` |
| `ssh chedam@chedam` timed out | Windows cannot resolve a bare name | IP, `chedam.local`, or the alias |
| `-i $env:venkata\.ssh\...` not found | `$env:USERPROFILE` is a real variable, not a placeholder | Keep `$env:USERPROFILE` |
| `Permission denied (publickey)` | Imager wrote an old remembered key (`…COL3o srey…`), not the PC's (`…LuhpI0dY chedam-dev`) | Re-flash; REMOVE old keys, BROWSE to `id_ed25519.pub` |
| A command pasted into Imager's key box | `Get-Content … \| Set-Clipboard` text pasted as the key | REMOVE, then BROWSE to the file |
| "REMOTE HOST IDENTIFICATION HAS CHANGED" | Expected after a re-flash (new host key) | `ssh-keygen -R 192.168.50.101` |
| Reservation saved as *Disabled* (TP-Link) | Router default | Tick it, then Enable Selected; leave ARP binding off |
| HDMI blank | `dmesg`: `vc4-drm: Cannot find any crtc or sizes` | Append `video=HDMI-A-1:1280x720@60D` to the single line in `/boot/firmware/cmdline.txt`, then reboot |
| Lines after `sudo cp` lost | The sudo password prompt ate the pasted lines | Paste one command at a time when sudo may prompt |

HDMI fix commands:

```
sudo cp /boot/firmware/cmdline.txt /boot/firmware/cmdline.txt.bak
sudo sed -i '1 s/$/ video=HDMI-A-1:1280x720@60D/' /boot/firmware/cmdline.txt
sudo reboot
```

## Lessons

- Before flashing, check that the key shown in Imager ends the same as `type C:\Users\Venkata\.ssh\id_ed25519.pub`. Imager remembers old keys.
- Always back up `.ssh` before changes.
- With password login off, losing `id_ed25519` means re-flashing or using a keyboard and screen.
- No passwords or key contents are stored in the repo.
