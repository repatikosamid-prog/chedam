# P5 Connect and enrich started; web store moves onto the Pi

## Summary

Sreya: "continue to P5, deploy to the Pi; next, slight changes in plans: e-commerce hosting using the same Pi for the business." P5 is planned (`docs/P5-mini-spec.md`, `docs/sprints/Sprint-5.md`, 9 steps) and built the same way as P2-P4: each step gets its own hub test suite (run once), a client build, a deploy to the Pi and a commit. The full suites, Pi test runs and browser walkthroughs wait for the next test week. The web store change is recorded as **DL-214**: the shop will run on the store's own Pi through an outbound tunnel, replacing option A of DL-114 (a static host). It is the next sprint after P5.

## Decision: the web store on the Pi (DL-214)

- The shop runs as a **separate process under its own user** with a read-only copy of the catalogue that the hub refreshes. It never touches the hub's database.
- It is reached through an **outbound tunnel** on the owner's domain (Cloudflare Tunnel). No port forwarding is needed; the TELUS modem has none anyway.
- Online checkout uses the processor's hosted page (Square, the same account as the terminal). Paid orders come back as pick-up orders with stock reserved.
- Rate limits apply, and the shop stops itself before it can slow the tills. Production hardware is the Pi 4.
- Accepted trade-off: the shop is down whenever the store's power or internet is.
- Manager remote access (FR-12.06) uses the same tunnel and moves to that sprint.

## Found and fixed

- **Backups did not keep the hub's own keys.** A backup saved the database and the HTTPS certificate authority, but not `pb_data/chedam-hr.key`. After a restore onto a new card, the employees' SIN and bank details (P4) could not be read. `chedam-backup` now saves `pb_data/chedam-*.key` beside each backup (`.keys`, encrypted with the backup key). The restore puts them back and keeps the current ones aside (DL-216).

## Failed cases and fixes (all in the new suites, before deploying)

- Step 5: the summary could not be uploaded on a hub that had never made a backup: `pb_data/backup` did not exist yet for the scratch file. `cloud.js` now creates the folder first.
- Step 6: the test created a product through an endpoint that does not exist; it now creates it with the product import. The P1 import/export suite found that the new P5 tables were in no group of the "Export data" chooser; they now are (and hidden tokens stay out).
- Step 6: the Import screen needed `catalogue.edit`, which would have kept the accountant from importing open bills. It now opens for anyone with one of the import permissions; the hub checks each import.
- Step 7: route helpers declared at the top of `reference.pb.js` were not visible inside handlers (the known PocketBase rule); moved into `lib/reference.js`. Products have no SKU field, so the SKU match was removed.
- Step 8: Python's `pwd` module does not exist on Windows, which stopped the helper's self-test on the PC; it is imported only where it exists. The "Add a key" form would have replaced every key (the screen only sees masked keys); the hub now takes add / remove as well as replace. A test picked the first start request instead of the latest.

- The fake Square ignored `fake.down = true`: the server read `st.down`. Fixed with a getter and setter in the fake.
- A checkout timeout setting of 0 seconds was read as "not set" (300 s), because of `||`. Fixed: only a missing value means 300.
- A linked-payment test sold more towels than the sample stock has. The test now receives stock first.
- The refund test read the refundable amounts from `returns/find`, a short list. They come from `returns/sale/{id}`; the test was fixed.
- Cloud uploads made a new "Chedam" folder on each upload and kept using an expired access token. The code used a stale copy of the link record. Fixed: it re-reads the record; on a 401 it refreshes the sign-in and tries once more.
- Svelte warned that `returnId` (Returns screen) was not reactive, so the refund chooser would keep the old return id after "another return". It is now `$state`.
