## 2. Admin access

### Failed case: `Permission denied (publickey)` when restoring sudo

- The `ssh -t chedam "…sudo tee…"` command was typed **inside an SSH session on the Pi** (prompt `chedam@chedam:~ $`).
- So the Pi tried to SSH into itself and had no key for that. Re-flashing was not needed.
- Fix: run only the inner command on the Pi:

```
echo 'chedam ALL=(ALL) NOPASSWD:ALL' | sudo tee /etc/sudoers.d/010-chedam && sudo chmod 440 /etc/sudoers.d/010-chedam
sudo -n true && echo OK
```

### Design choices

- **Common fields:** `id` (a device may create it offline), `created_at`, `updated_at`, `created_by`, `updated_by`, `device_id`, `deleted_at`. `updated_by` was added beyond the spec's list, so each change records who made it.
- **The event log runs inside the same transaction** as the change (`onRecord*Execute` + `runInTransaction`). If the event can't be written, the change is rolled back, so the log never misses a write.
- **Actor and device are stamped by the hub** in request hooks. A client cannot forge `created_by`, and the device comes from the `X-Chedam-Device` header (verified in step 4).
- **Hidden fields** (`pin_hash`, `recovery_code_hash`, `key_hash`, `pairing_code_hash`) never reach the API or the log.
- **Role levels:** owner 100, manager 80, accountant 50, cashier 40, staff 30. Owner-only permissions: modules.manage, setup.run, owner.manage, backups.restore, updates.install.
- **Sample data is separate** from real migrations, so a store hub never receives demo records.

### Who may do what (summary of the access map)

- **Anyone signed in:** reads the business profile, locations, settings, modules, permissions, roles and storage areas.
- **People:** list with users.view; a person can view and edit their own record (name, email, phone, language, accessibility, password only); add/edit others needs users.manage; giving or changing roles needs access.manage; no hard delete.
- **Overrides:** access.manage only; never on yourself; only on people below you; never grant what you don't hold; owner-only permissions only by the owner.
- **Roles:** templates can't be deleted; only the owner edits templates; the owner role always holds everything; managers create and edit only roles below their own level.
- **Modules:** owner only; only `enabled` can change; core can't be switched off; "later" modules can't be switched on; who/when stamped.
- **Settings:** `security.*` owner only; keys can't be renamed.
- **Audit log:** events.view. Tasks: tasks.view / tasks.manage (the assignee may update status/note). Devices: devices.view / devices.manage. Backups and updates: read-only through the API.

## 11. Forgot PIN: temporary PIN (Sreya's decision)

Sreya: "manager reset temporary and user need to reset again".

- A PIN set by someone else (manager with users.manage above the person, or superuser) is **temporary**. It works for 24 h (`security.temp_pin_hours`).
- With a temporary PIN, the hub allows only these until a new PIN is chosen: setting your own PIN, `access/me`, `devices/me` and sign-out. Everything else answers 403 "Choose your own new PIN first." (`auth.pinChangeGate`, run in the request middleware).
- The new PIN must differ from the temporary one, and the PIN rules apply. An expired temporary PIN is refused with a clear message.
- `pin_must_change` and `pin_temp_expires_at` are protected fields, and both changes are in the audit log.
- Migration `1791200005_p0_temp_pin.js` (reversible). Tests: `step3b-temp-pin.test.mjs`, 14/14.
