# P0 gate: power pull ×10 passed after two real fixes (Wi-Fi lost at boot, confirmed writes lost); untrusted-certificate warning

## Summary

- **New Android phone** ("1plus", Android 10, Chrome 151) worked without the certificate installed. Not a bug: Chrome lets a person tap through "Your connection is not private". The app now warns with an amber bar (DL-62).
- **Power-pull gate test (NFR-09, ×10): PASS on run 3.** 47,573 confirmed writes, **0 lost**, 0 duplicates, audit log complete, both databases intact, the real hub restarted by itself every time (48-78 s).
- It found two real problems first, both fixed and proven:
  1. **Wi-Fi lost after power cuts during boot**: the Wi-Fi settings files were left empty. Fix: `chedam-netguard` (DL-60), tested by deleting the profile: recovered unattended in 127 s.
  2. **Confirmed writes lost in a power cut** (23 of 1,646): SQLite confirmed before writing to the card. Fix: `synchronous=FULL` (DL-61).
- My test script crashed once (too short a timeout after a cold boot); fixed, and confirmed writes are now kept in a file as they happen.
- Gate status: 3-device login ✅, update + rollback ✅, backup + restore ✅, memory under load ✅, power pull ×10 ✅. Left: camera over HTTPS.

## 3. Run 1: the writer crashed, then the Pi came back without Wi-Fi

| Time (UTC) | What happened |
| --- | --- |
| 16:04 | "Hub gone" for 6 s, no reboot: the laptop's SSH tunnel dropped (Wi-Fi blip); correctly not counted. Sreya had not pulled yet |
| 16:06 | Pull 1 → back after a reboot at 16:07 |
| 16:07 | **My script crashed** while checking: listing ~17,000 records on a freshly booted Pi Zero took more than its 4 s timeout. The list of confirmed writes was only in memory, so this cycle could not be judged |
| after | Sreya pulled two more times; the Pi stopped answering (ping, SSH) |

On the hub's monitor: a normal login prompt, but "My IP address is **127.0.1.1**" (no network address). The router listed 3 Wi-Fi devices, none the Pi. Sreya connected a keyboard:

| Check | Result |
| --- | --- |
| `nmcli dev status` | `wlan0 wifi disconnected` |
| `rfkill list` | not blocked |
| `dmesg` | Wi-Fi firmware loaded normally (BCM43430/1) |
| `nmcli con show` | **only `lo`**: no Wi-Fi network known at all |

Sreya reconnected with `sudo nmcli dev wifi connect "TP-LINK_2CBE" password "…" ifname wlan0` (her password, typed by her), and the hub was back at 192.168.50.101.

### Root cause

- Raspberry Pi OS 13 keeps the Imager Wi-Fi settings in `/etc/netplan/90-NM-*.yaml`, from which NetworkManager's profile is generated **at every boot**.
- Both files were **0 bytes**: they are rewritten during boot, and a power cut before the data reached the card left them empty (the new length was saved, the contents were not).
- Sreya's new profile carried yesterday's time (04:49), because the Pi's clock was wrong at boot: no network to set it and no RTC (the DL-23 risk, seen live).
- Data after these three cuts: both databases intact; 17,863 test records = 17,863 audit entries.
- My setup script only adds a power-save setting; it does not touch the Wi-Fi profiles.

### Fix: chedam-netguard (DL-60)

- `hub/system/chedam-netguard` + `.service` + `.timer` (every minute), installed by `deploy.sh` and `setup-hub.sh`:
  - **online**: an fsync'd spare copy of each valid Wi-Fi profile (must have an SSID and not be empty);
  - **2 min without an address**: restore the spare copies if no Wi-Fi network is known, then reconnect;
  - **10 min**: reboot, at most once an hour.
- **Controlled test on the Pi:** the profile was removed and Wi-Fi disconnected (with a 9-minute safety timer that would have put it back). Log:
  - 09:43:55 profile removed;
  - 09:46:33 "no Wi-Fi network known after 127 s … restored spare copies";
  - 09:46:37 "reconnected wlan0".

  The hub was back at 192.168.50.101 with nobody touching it. The safety net was not needed (removed).

### Fix: test script

- Checks after a reboot get 60 s with 3 attempts, and a failed check is reported, not a crash.
- Every confirmed write is appended to a file at once.

## 4. Run 2: confirmed writes lost (stopped after cycle 1)

| Check | Result |
| --- | --- |
| Integrity, duplicates, audit, hub restart | all fine |
| **Confirmed writes lost** | **23 of 1,646** |

- **Cause:** PocketBase opens SQLite in WAL mode with `synchronous=NORMAL`, which confirms a commit before forcing it onto the card. In a power cut the last confirmed transactions can vanish. That breaks NFR-02 ("no lost or duplicated sales").
- **Fix (DL-61):** `hub/pb_hooks/durability.pb.js` sets `PRAGMA synchronous = FULL` on PocketBase's single non-concurrent (write) connection before every request, at start-up and every minute.
- Health page item "Saved before confirming" (bad if not FULL); test added; **329** tests pass.
- On the Pi: "Saved before confirming: Yes"; 30 writes in 2,147 ms (about 70 ms each, including the audit entry).
- Report kept: `docs/gate/powertest-2026-10-06-run2-synchronous-normal.json`.

## 6. Session 2: status check and a race fix

- Git: clean, `main` in sync with GitHub before starting. The Pi runs `dev-484c657`; the later commit `aebd3d5` was documents only.
- Full test run (`PB_BIN=C:/Tools/pocketbase.exe node hub/tests/run-all.mjs`): **1 failure**, `step9-updates` "one urgent task". It passed 3 times when run alone, so it was intermittent.
- **Cause (a real bug, not only the test):** when the hub applies an install result, it saved the update record and then its urgent task as two separate writes. The every-minute job and the status screen can both apply the same result at the same moment, so a reader could see "rolled back" before the task existed, and two appliers could each raise a task. `lib/backup.js` had the same pattern.
- **Fix (commit `85da79a`):** in `hub/pb_hooks/lib/updates.js` and `hub/pb_hooks/lib/backup.js`, finding the record, saving it and raising/closing the task now run in one transaction. The hub has a single writer, so the second applier waits, then finds nothing left to apply.
- **Verified:** full run 329/329 passed; `step9-updates` and `step7-backups` then passed 5 times in a row each.
- Not deployed yet: needs Sreya's go-ahead.
